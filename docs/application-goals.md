# アプリ構成と目標からの実行 — 設計と検証方針

作成日: 2026-09-25（第1段階の実装状況を2026-09-26に更新）

ステータス: 第1段階（DBなしアプリ）は実装・実Docker検証済み。修正前後の確認範囲は[検証結果](demo.md#2026-09-26の実docker検証結果)を参照する。第2段階（PostgreSQL対応）は計画であり、未実装。以下のDBなしYAMLは現行CLIの形式であり、DBありYAMLは第2段階の構想例。

## 検証したい価値

アプリケーションを作る文脈のまま、動かして確かめるところまで進める。アプリ構成とは別に、同じ依存関係や操作順序をパイプラインへ書く負担を減らせるかを検証する。

[最初のPoC](initial-poc.md)では、固定のAPI・DB・データセットを対象に、観測・再計画・実行の一周を確認した。一方、操作の依存関係はほぼ一本道で、別アプリを扱う際の記述負担や再利用性はまだ確認できていない。

今回は小さな別アプリを持ち込み、アプリ固有の処理を実行基盤に追加せずに扱える範囲と、利用者による補足が必要な情報を明らかにする。一般的なCI/CDや既存の構成管理方式に対する優位性・新規性を、この実験だけで結論付けない。

## 題材と範囲

| 構成 | アプリの例 | 確かめたいこと |
| --- | --- | --- |
| DBなし | 固定のメッセージを返すGo HTTPアプリ | DBの存在を前提とせず、ビルド・起動・確認を計画できる |
| PostgreSQLあり | メモを保存・取得する小さなGo API | DBへの依存と接続情報から、DB準備・API起動の関係を導ける |

一度に扱うのは一つのenvironment、アプリ一つ、任意でPostgreSQL一つとする。二つの構成を同じ実行基盤で扱い、アプリの変更時にPlanner・Runtimeへアプリ名や固有データの分岐を追加しないことを目指す。

実行先は引き続きローカルDockerとする。Dockerfileの標準的なビルドとコンテナ起動を基盤の操作として用意し、起動コマンドは原則としてイメージのENTRYPOINT/CMDを使う。

## 入力の案

構成、確認方法、目標を一つの文書内で分ける。構成は何を動かすか、確認方法は何をもって利用可能・検証済みとするか、目標はどこまで達成したいかを表す。

DBを使わない場合の例:

```yaml
environment: hello-preview

application:
  build:
    context: ./apps/hello
    dockerfile: Dockerfile
  port: 8080

checks:
  readiness:
    http:
      path: /health
      status: 200
  verification:
    http:
      path: /message
      status: 200
      bodyEquals: hello

goal:
  state: verified
```

`context`は設定ファイルのあるディレクトリからの相対パス、`dockerfile`はcontext内の相対パスとする。context外のDockerfileは対象外とする。入力の取り込みと固定方法は後述する。

DBを使う場合の例:

```yaml
environment: notes-preview

application:
  build:
    context: ./apps/notes
    dockerfile: Dockerfile
  port: 8080
  bindings:
    DATABASE_URL:
      resource: database

resources:
  database:
    type: postgres

checks:
  readiness:
    http:
      path: /health
      status: 200
  verification:
    http:
      path: /self-check
      status: 200
      bodyEquals: ok

goal:
  state: verified
```

`bindings`の参照から、必要なDBとアプリへの接続先の受け渡しを判断する。別途`dependsOn`やDB作成ステップを重複記述させない。秘密値をこのYAMLへ記載させる設計にはしない。

目標の`ready`は起動とreadiness確認まで、`verified`はさらにverification成功までを要求する。readiness成功と業務上の検証成功は区別する。検証を要求したのに確認方法がない場合は、暗黙に成功とせず入力エラーとする。

`/self-check`はDBへの保存・取得を確かめるデモ用の案であり、全アプリへ要求する共通エンドポイントではない。確認内容は利用者の知識で、システムが自動的に推測するものではない。

## システムが判断することと、利用者が用意すること

| 情報・処理 | 担当 |
| --- | --- |
| アプリのコード、Dockerfile、起動方法 | 利用者が用意する |
| 必要なDBと接続先を受け取る環境変数 | 利用者が構成として指定する |
| readinessと検証内容 | 利用者が指定する |
| イメージが必要か、DBを作る必要があるか、アプリを更新する必要があるか | システムが目標と観測状態から判断する |
| 操作の前提条件・予測結果・実行・観測 | 今回は基盤側の標準操作として実装する |
| アプリ固有のスキーマ・migration・テストデータ | アプリ側の責務とし、必要な実行契約は明示する |

DBの起動だけでは、スキーマやデータの準備まで完了したとはみなさない。`notes-preview`環境で動かすメモAPI自身が、起動時に初期テーブルを作成する方針とする。基盤はSQLやアプリ固有のスキーマを知らない。この実験では構成による計画の違いに集中し、独立したmigration操作や既存スキーマからの移行は対象外とする。

任意のユーザー定義操作を登録する汎用プラグイン機構は、この段階では作らない。標準操作で吸収できない差分を先に観察し、その後に拡張点を決める。

## 成功条件と確認方法

| 状況 | 期待する結果 |
| --- | --- |
| DBなし・空の環境 | DB操作を含まず、ビルド・起動・確認で目標を達成する |
| DBあり・空の環境 | DBの依存を満たしてからAPIを起動し、DBを使った確認で達成する |
| 対象イメージが準備済み | 同じ入力に対応することを確認し、不要なビルドを省く |
| DBが利用可能で構成に適合 | DBを再作成せず利用する |
| 目標・構成が変わらず達成済み | 再ビルド・再デプロイなどの不要な変更を行わない |
| アプリ入力が変更された | 新しい入力に対応するイメージと実リソースを確認し、古い検証成功を流用しない |
| 利用者の記述を比較 | 操作順序や依存関係の二重記述がなく、補足が必要な知識を説明できる |

イメージタグ名だけで同一性を判断しない。後述するビルド入力の識別、イメージID、実行時設定と検証成功の対応で判断する。最初から汎用のビルドキャッシュを作ることは目的にしない。

各段階ではまず手動でアプリの動作と計画ログを確認する。自動テストは計画の違い、不要な操作の省略、成功記録失効など、繰り返し守りたい性質に絞る。既存の固定デモに依存するテストは新しいモデルに合わせて更新し、実Dockerの自動テストを追加・置換する範囲は手動確認後の必要性で判断する。

動作したという結果だけでなく、アプリ側に追加したコード・設定と、利用者が知る必要のあった情報を記録する。複雑な手順をアプリ側へ移しただけなら、その負担も評価に含める。

## 今回扱わないもの

- Kubernetes対応、Namespaceとの実際の対応付け、マルチテナント制御。
- 複数アプリの同時更新、共有DBの所有・更新調停。
- 全コミットを順番に処理するキュー、互換性のないmigrationの順序制御。
- 自動復旧、rollback、永続化、分散worker。
- AIによる操作生成、汎用プラグイン機構、YAML形式の最終確定。

environmentは目標に基づく管理対象のまとまりとし、権限境界とは別概念として扱う。将来のKubernetes対応でも、environmentの指定によって実行主体の権限が広がる設計にはしない。

## 合意した進め方

検証ポイントを明確にするため、それ以外の機能は一旦置いておく。既存の目標形式との互換性は維持せず、新しい形式へ更新する。以前のPoCはGit履歴から参照でき、必要になればその時点のcommitへtagを付ける。現時点でtagは作成しない。

ビルド入力はCLI起動時にコピーして確定し、入力の識別とビルドで同じコピーを使う。ソースの変更を反映するときはCLIを再実行する。継続観測と1操作ごとの再計画は維持するが、ソースのリアルタイム監視は今回実装しない。起動時固定は今回の範囲を絞るための制約であり、将来の構成変更への追従を禁止する設計ではない。

### 第1段階：DBなしのアプリで一周つなぐ

| 変更対象 | 変更内容 |
| --- | --- |
| `internal/goalfile` | 構成・確認方法・目標を持つ新形式を読み込み、未知の項目や不正な参照・値を検証する |
| `internal/planning` | 固定のAPIバージョン・データセットを前提とするモデルから、対象イメージ・アプリの準備状態・検証の有効性を扱うモデルへ更新する |
| `internal/control` | 読み込み・観測・計画・先頭1操作の実行という責務を維持し、新モデルに接続する |
| `internal/dockerruntime` | ビルド、対象イメージによる起動・更新、HTTPによるreadinessと検証を実装する。所有権確認・cleanup・操作期限の扱いを引き継ぐ |
| `cmd/goal-executor` | 新形式を制御ループへ接続し、計画・操作理由・観測結果の記録を維持する |
| サンプルアプリ・設定・文書 | DB不要のGo HTTPアプリ、Dockerfile、新形式の設定、実行手順を用意する。旧サンプルと説明を更新する |

探索処理は引き続き実リソースに接続しない。`ready`と`verified`で必要な操作が変わり、対象イメージが準備済みならビルドを省略できるようにする。HTTPの確認先や期待値は設定から受け取り、アプリ固有の応答をRuntimeへ埋め込まない。

第1段階の完了条件:

- 空の環境からビルド・起動・確認を通して達成し、DB操作が発生しない。
- `ready`ではreadinessまで、`verified`では指定した応答の検証までを要求する。
- 同じ入力で再実行した場合、イメージとコンテナを再利用する。成功記録はメモリ上に限定するため、CLI再起動後の再検証は許容する。
- ソースを変更して再実行すると新しいビルド・更新へ進み、以前の構成に対する検証成功を使わない。
- HTTP応答が期待に反する場合は達成と判定しない。

検証は、入力検証・計画の分岐・成功記録の失効を通常テストで確認し、Dockerで上記の代表的な動作を手動確認する。旧モデルに依存するテストは新モデルへ更新し、探索・観測と予測の分離・所有権確認などの検証観点は残す。実Dockerの自動テストを増やすかは、手動確認後の必要性で判断する。

### 第2段階：DBありのアプリを同じ仕組みに載せる

`resources`と`bindings`からDBへの依存と接続先を導き、メモAPIを起動する。初期化はアプリ自身に任せ、基盤はDBの利用可否とアプリの確認結果を観測する。DB再利用を確認し、アプリ固有の分岐をPlanner・Runtimeへ追加せずに済むかを評価する。

第1段階で追加したモデルを実際に再利用できるかを見てから、DB操作の変更範囲と検証方法を具体化する。

## 第1段階の具体的な仕様と検証方針

### ビルド入力の取り込み

1. 設定ファイルを読み、contextとその内部のDockerfileを解決する。
2. 使用する除外ルールを選び、それを適用したコンテキストのファイルと、Dockerfile・使用するignoreファイルを一時ディレクトリへコピーする。
3. 選択したDockerfileのcontext内の相対パスと、Dockerfile・除外ルールを含むコピー済みの入力一式の相対パス・内容・実行権限からハッシュを計算する。同じファイル一式でもDockerfileの選択が違えば別の入力として扱う。
4. 同じコピーをDockerへ渡してビルドする。

ハッシュ計算後に元のソースが変更されても、識別した入力と実際のビルド入力が食い違わないようにする。コピーの取り込み中は編集しない前提とし、取り込み完了後は元の作業ツリーを編集してよい。その変更は次回CLI起動時に反映する。Gitのcommitや作業ツリーを戻す操作は行わない。

取り込み対象にシンボリックリンクが含まれていた場合はエラーにする。今回はリンク先の取り込みやcontext外参照には対応しない。

#### `.dockerignore`の役割と取り込み方

`.dockerignore`はビルドコンテキストから除外するファイルを指定する。今回もその範囲に合わせてコピー対象を選び、除外された通常のファイルの変更で不要な再ビルドが発生しないようにする。入力を固定するのはコピー処理であり、`.dockerignore`自体ではない。

使用するルールは、指定したDockerfileと同じ場所にある`<Dockerfile名>.dockerignore`を優先し、なければcontext直下の`.dockerignore`を使う。両者を結合しない。`!`による再包含と、後のルールが優先される挙動も扱う。[Docker公式仕様](https://docs.docker.com/build/concepts/context/#dockerignore-files)

ローカルディレクトリを使うBuildKitでは、Dockerfileをビルド定義として、ignoreファイルを除外ルールとして読み込む処理と、除外ルールを適用したコンテキストの取り込みは分かれている。「除外済みコンテキストからDockerfileを探す」という前提にはしない。[BuildKitの実装](https://github.com/moby/buildkit/blob/master/frontend/dockerui/config.go)

今回の一時ディレクトリは、コンテキストだけでなくビルド入力一式を固定するためのものとする。Dockerfileと使用するignoreファイルは、それ自身が除外指定されていてもコピーする。Dockerにはコピー側を参照させ、元の作業ツリーのDockerfileや除外ルールを使い続けない。除外指定はコピー側にも保持し、除外された両ファイルを`COPY`や`ADD`の対象へ戻すことはしない。

例えば`.dockerignore`に`Dockerfile`と`.dockerignore`を指定した場合も、この2ファイルはビルド入力として固定・識別する。一方、除外した通常のログファイルなどはコピーも識別の対象にもしない。これにより、ビルド手順や除外ルールの変更を入力の変更として扱える。

パターン解釈には`github.com/moby/patternmatcher v0.6.1`を使用する。Docker公式が案内している実装であり、`ignorefile.ReadAll`でルールを読み、`PatternMatcher.MatchesOrParentMatches`で照合する。この版の`go.mod`には追加のモジュール依存がない。[API](https://pkg.go.dev/github.com/moby/patternmatcher@v0.6.1)、[ignorefile API](https://pkg.go.dev/github.com/moby/patternmatcher@v0.6.1/ignorefile)、[go.mod](https://github.com/moby/patternmatcher/blob/v0.6.1/go.mod)

#### 固定する範囲の限界

固定するのはローカルのビルド入力であり、可変のベースイメージやビルド中に取得する依存まで固定するものではない。入力ハッシュは完全な再現可能ビルドを保証せず、外部依存の更新を自動検知して再ビルドすることも今回の対象外とする。

### 実行中の設定変更

アプリ構成とチェック内容は起動時に固定する。1操作の完了後、次の観測・計画に入る前にYAMLを読み直し、起動時の設定と意味上の値を比較する。

| 変更内容 | 挙動 |
| --- | --- |
| `goal.state`のみ変更 | 次のループで反映し、再計画する |
| アプリ構成・チェック・`environment`を変更 | 新しい操作を止め、変更の反映には再起動が必要と通知する |
| YAMLが一時的に不正 | 操作を止め、修正を待つ |
| コメントやキーの順序だけ変更 | 意味上の変更として扱わない |

固定対象を起動時の内容へ戻せば、CLIを再起動せず再開できる。操作中の設定変更を理由にビルドなどを途中で打ち切らず、変更は操作の区切りで検知する。停止中も既存コンテナは残し、暗黙のcleanupはしない。

`ready`から`verified`へ切り替える場合は、起動時からverificationの定義を用意しておく。検証を要求しても定義がなければ入力エラーとして扱う。

### リソースの再利用と検証成功

HTTPチェックは指定したパスの応答ステータスと、指定があれば本文の完全一致を確認する。リダイレクトは追跡せず、3xxも元の応答として判定する。

- ビルド入力のハッシュに対応するローカルイメージを再利用する。
- コンテナは所有権、実際のイメージID、起動設定が一致する場合に再利用する。
- 検証成功は、対象コンテナのID・起動時刻・チェック内容に結びつけてメモリ上に保持する。
- コンテナの置き換えや再起動で成功記録を失効させる。CLI再起動時にも再検証する。

検証成功は対象の構成に対して確認が成功した記録であり、任意のアプリ内部データがその後も変化していないことを保証しない。DBを扱う第2段階では、この前提に応じた検証範囲を改めて具体化する。

### 検証項目

通常の自動テストでは、以下の性質を確認する。

- 取り込み後に元ファイルを変更しても、固定した入力とその識別が変わらない。
- 対象ファイルの変更は入力の識別に反映され、除外された通常のファイルの変更は反映されない。
- Dockerfileと使用するignoreファイルは、自身の除外指定にかかわらず固定・識別される。Dockerfile専用のignoreファイルの優先と、`!`による再包含を確認する。
- コピー対象が同じでも、使用するDockerfileの選択変更で入力IDが変わる。
- 設定変更の区分に応じて反映・停止・再開し、コメントやキーの順序では停止しない。
- `ready`と`verified`、イメージの有無などの状態に応じて必要な操作だけを計画する。
- コンテナの置き換えや再起動で古い成功記録を利用しない。
- HTTPチェックがリダイレクト先の成功応答で誤って達成と判定しない。
- 探索の最短経路・同数時の選択順・探索上限、観測／操作失敗時の停止、達成後の目標変更、環境名変更時の保留、待機のキャンセルという既存の検証観点を維持する。

実Dockerでは、以下をまず手動で確認する。

| 状況 | 確認する結果 |
| --- | --- |
| 空の環境から開始 | ビルド・起動・検証を通して`verified`に到達する |
| 同じ入力でCLIを再実行 | イメージとコンテナを再利用し、検証を再実行する |
| ソースを変更してCLIを再実行 | 新しい入力をビルドし、コンテナを更新する |
| 実行中に`ready`から`verified`へ変更 | 再ビルドや再起動をせず、検証へ進む |
| HTTP応答が期待と異なる | 達成と判定しない |

第1段階の実装と通常テストは本リポジトリに置く。Dockerへの実接続と環境操作は、対象と影響を明示したうえで別途確認する。
